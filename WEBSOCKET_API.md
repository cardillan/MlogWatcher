# WebSocket API

The mod provides a WebSocket API, which can be used to update logic processors and schematics in the game. The API can be called from a web page as well as a locally run app.

The WebSocket server runs on port `9992` by default, but this can be changed in the configuration. The most recent interface runs on the `/v1` path. For connecting to a game running on a local computer, use the `localhost:9992/v1` URL. (It is also possible to connect to a game running on another device, assuming the connection can be made and isn't blocked by a firewall.)

> [!NOTE]
> When no path is specified in the URL, the [legacy API](#legacy-api) is used. When any other path is specified, the server doesn't process or respond to the request.

The API uses JSON for communication. An instance of the [`Request` class](CLASSES.md#class-request) must be sent to the server. The class has the following attributes:

* `method`: the method to call on the server (see below)
* `method_version`: the version of the method to call. 
* `invocation_id`: the id generated by the client. Responses sent by the server to a specific request are marked with the same `invocation_id`. 
* `params`: the method's parameters. The specific instance of this object depends on the method being called.

When the request is handled, the server sends back a [`Response` object](CLASSES.md#class-response). The class has the following attributes:

* `status`: `success` in case of successfully completed request, `error` otherwise.
* `invocation_id`: the id of the request this response is for.
* `result_type`: type of the result contained in this response.
* `result`: actual result returned by the server.

A response may not contain any result. In this case, both `result_type` and `result` will be set to `null`. Such a response is called an _empty response_.

When `status` is set to `error`, the result type will be set to `text_result`. The `result` field will contain a [`TextResult` instance](CLASSES.md#class-textresult) containing an error code in the `text` field. Currently, possible error codes are:

 * `invalid_arguments`: the request instance couldn't be correctly decoded. 
 * `invalid_program_id`: the [program id](CLASSES.md#class-programid) specified in the request is invalid.
 * `invalid_version_selection`: the [version selection]() specified in the request is invalid.
 * `no_processor_attached`: no logic processor was selected in the game.
 * `no_active_map`: no map is currently loaded in the game.
 * `no_processors_found`: no logic processor matching the selection criteria was found.
 * `schematic_import_failed`: the schematic couldn't be imported (possibly because the schematic content is corrupted).
 * `unknown_method`: the method specified in the request doesn't exist.
 * `unsupported_method_version`: the version of the method specified in the request is not supported.
 * `internal_error`: an internal error occurred.
 * `no_schematic_selected`: no schematic was selected in the game.
 * `schematic_extraction_failed`: the selected schematic couldn't be extracted from the game.

## API methods

### Method `update_selected_processor`

This method injects mlog code into the selected processor on the map.

#### Request parameters

[`UpdateSelectedProcessorParams`](CLASSES.md#class-updateselectedprocessorparams) 

* `code`: the source code of the mlog program.

#### Responses

**Success**

An empty `success` response is returned if the selected processor was updated successfully.

**Errors**

Upon error, an `error` response is sent. Errors pertaining to this method are:

* `no_processor_attached`: no processor is currently selected.

### Method `update_processors_on_map`

This method finds all compatible processors on the map and injects the provided mlog code into each of them. The program ID is used for processor identification. The caller provides a program ID for locating the processors, and the server extracts the program ID from processors on the map. If there's a match, the program is injected into the processor. A typical use-case is updating all processors on the map with a new version of the program.

#### Request parameters

[`UpdateProcessorsOnMapParams` instance](CLASSES.md#class-updateprocessorsonmapparams)

* `code`: the source code of the mlog program.
* `program_id`: a [program ID](CLASSES.md#class-programid). Contains a prefix and version numbers. To match, the processor's ID must have the same prefix and a compatible version number.
* `variableName`: name of the variable which should contain the program ID. The server looks for this variable in processors. The variable name may not be overridden by the mod's configuration.
* `version_selection`: string. One of: 
  * `exact`: only processors whose version number exactly mathes the one specified in the program ID are updated.
  * `compatible`: processors whose version number is lower than or equal to the one specified in the program ID are updated.
  * `any`: all processors with a matching prefix are updated, regardless of the version number (used to perform a downgrade).

#### Responses

**Success**

* `status`: `success`
* `result_type`: `processor_update_result`
* `result`: [`ProcessorUpdateResults`](CLASSES.md#class-processorupdateresults) instance containing an array of `LogicProcessor` instances, one for each matching processor found, with the following attributes:
  * `x`, `y`: the position of the processor on the map.
  * `type`: the type of the processor asr reported by the game (in vannilla, one of `micro-processor`, `logic-processor`, `hyper-processor` or `world-processor`; mods could add more processor types).
  * `program_id`: the [program ID](CLASSES.md#class-programid) of the processor before the update.
  * `status`: string. One of:
    * `updated`: the processor was updated successfully.
    * `incompatible_version`: the processor's version number was not matched by `version_selection`.
    * `missing_program_id`: the processor has no program ID at all.

Processors with valid, but not matching program IDs are not included in the response.

**Errors**

Upon error, an `error` response is sent. Errors pertaining to this method are:

* `invalid_program_id`: the `program_id` parameter has an invalid format.
* `invalid_version_selection`: the `version_selection` parameter has an unknown value.
* `no_active_map`: no map is currently active in the game.
* `no_processors_found`: no compatible processor was found on the map.

### Method `put_schematic_in_library`

This method adds a schematic to the Schematics library. Schematics are updated regardless of the state of the game. When the game is running, only a message is briefly shown in the game. When the game is paused or not active at all, the imported schematic is shown on screen.

#### Request parameters

[`PutSchematicInLibraryParams` instance](CLASSES.md#class-putschematicinlibraryparams)

* `schematic`: a Base-64 encoded schematic (the format used by the game to copy the schematic to the clipoard).
* `overwrite`: boolean. When `true`, a schematic with the same name and an `MlogWatcher` tag is overwritten if it already exists in the library. When `false`, the new schematic is always added to the library. 

#### Responses

**Success**

An empty `success` response is returned when the schematic was added successfully.

**Errors**

Upon error, an `error` response is sent. Errors pertaining to this method are:

* `schematic_import_failed`: the import has failed. The most probable cause is that the schematic couldn't be properly decoded.

### Method `extract_selected_processor_code`

This method extracts and returns the mlog code from the selected processor on the map.

#### Request parameters

This method doesn't take any parameters (set `params` to `null`).

#### Responses

**Success**

* `status`: `success`
* `result_type`: `mlog_code_result`
* `result`: [`ProcessorExtractResults`](CLASSES.md#class-processorextractresults) instance containing the following attributes:
  * `code`: the source code of the extracted mlog program.

**Errors**

Upon error, an `error` response is sent. Errors pertaining to this method are:

* `no_processor_attached`: no processor is currently selected.

### Method `extract_selected_schematic`

This method extracts and returns the schematics whose details are currently being shown on the screen.

**Note:** Mindustry doesn't support accessing the currently displayed schematic directly. The mod uses a hack to obtain this schematic, but at this moment it only works when the schematic screen has been entered from the game, not from the main menu. 

#### Request parameters

This method doesn't take any parameters (set `params` to `null`).

#### Responses

**Success**

* `status`: `success`
* `result_type`: `text_result`
* `result`: [`TextResult`](CLASSES.md#class-textresult) instance containing the following attributes:
    * `text`: a Base-64 encoded schematic definition.

**Errors**

Upon error, an `error` response is sent. Errors pertaining to this method are:

* `no_schematic_selected`: no schematic is currently selected (the schematic details screen is not currently active).
* `schematic_extraction_failed`: the schematic is selected in-game, but couldn't be extracted. The most probable reason is that the schematic screen has been entered from the main menu.

## Legacy API

> [!NOTE]
> Do not use the legacy API for new developments. This API is not safe, as the received messages are sent directly to the selected processor without any validations, possibly overwriting the processor's code with incorrect data. 

The legacy API represents the Websocket interface provided by earlier versions of the mod. It is invoked when no path is specified in the URL.

The message sent to the server must be an unencoded mlog string. When a processor is selected, the received text is injected into it.

The server sends a simple text as a response to this call:

* `ok`: the processor was updated successfully.
* `no_processor`: no processor is selected in the game.
